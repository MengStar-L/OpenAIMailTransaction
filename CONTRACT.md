# Application contract

Go module: `openai-mail-transaction`. Embedded frontend in `web/` (vanilla HTML/CSS/JS, no build step). Go JSON HTTP server. All API dates RFC3339 UTC. UI Chinese; brand `拾光 · Atelier`. Minimal anime styling: milk-white and soft sky accents, generated cat illustration, bundled ZCOOL KuaiLe font, restrained motion and reduced-motion support. Keep functional labels and one page title; no decorative English subtitles or hero marketing copy. Pointer interactions have no outer focus ring; keyboard interactions retain inset focus indicators, hidden while the window is inactive. Poll every 5 seconds only while order active; countdown uses server time. API errors `{error:string, code?:string}`.

## Public API

- GET `/api/config` -> `{brand, mode:"demo"|"live", configured:bool, phone_enabled:bool, email_enabled:bool, background_type:"none"|"image"|"video", background_url:string, queue_default_minutes:10, queue_min_minutes:1, queue_max_minutes:1440, server_time:string}`.
- GET `/api/inventory` -> `{email:{count:number|null,status:"available"|"unavailable"|"unconfigured",updated_at:string|null,message:string,allocation_status:"unconfirmed"|"no_stock",allocation_checked_at:string|null},server_time:string}`. Read-only reference stock for the configured email service/domain within its price ceiling; positive counts do not guarantee that an allocation will succeed. Successful zero means zero quoted stock or the quoted price exceeds the ceiling; configuration/network/format errors return null, never an invented zero. Shared server cache: 30 seconds for success, 10 seconds for failure, coalesced across visitors; configuration and credential changes invalidate the cache key. Every email allocation result invalidates its matching quote cache. An explicit, certain `no_stock` rejection records a two-minute in-memory observation keyed by the actual allocation service/domain/price/credential, preserving the reference count; a quote refresh cannot clear it, while a successful matching allocation can. Other errors do not create a no-stock observation. `unconfirmed` makes no claim of allocatability. Page headers show reference count and recent refusal separately, refreshing every 30 seconds while visible and after allocations. No API credentials, account balance, or raw provider errors are exposed.
- POST `/api/redeem` body `{cdk:string,queue_minutes?:integer}` -> `{token:string, order:Order, server_time:string}`. CDK dictates kind/country/domain. The same CDK resumes its active order. A terminal, confirmed released/completed activation allows a new allocation while success quota remains. No allocation on refresh.
- POST `/api/orders/queue-wait` body `{queue_minutes:integer}` (Bearer token) updates only a queued email order and returns `{order:Order,server_time}`. The deadline stays anchored to the original request created_at, not the edit time. Shortening past elapsed time expires the queue locally and releases the voucher without upstream cancellation. Invalid/missing values return 400; a nonqueued or phone resource returns 409. Update, worker allocation and cancellation share the order lock. Administrator resources expose the same action under their own authenticated route.
- GET `/api/orders/current` (Authorization Bearer token) -> `{order:Order, server_time:string}`; backend refreshes upstream with throttling.
- POST `/api/orders/cancel` body `{}` (Bearer token) -> `{order:Order, server_time:string}`. A queued request cancels locally without an upstream release request. Once allocated, only a resource with no received code can be cancelled for another attempt; upstream release must be confirmed. Cancellation does not consume success quota.
- New SMSBower phone activations do not carry a synthetic two-minute cancellation delay. After checking for a late code, attempt cancellation immediately. An actual `EARLY_CANCEL_DENIED` schedules a local ten-second retry throttle, not a new two-minute minimum age. Honor explicit HTTP Retry-After and persisted deadlines on pre-upgrade orders. Unknown cancellation replies never prove release.
- POST `/api/orders/next-code` body `{round:1..3}` (Bearer token) -> `{order:Order, server_time:string}`. `round` must be the client's currently displayed `mail_round`. Only a received, unexpired email activation below round 3 may request the next round. A stale round returns the current order without another state-changing upstream request. History is retained while the current `code` becomes empty. Never automatically replay an uncertain next-round request.
- POST `/api/orders/complete` body `{}` (Bearer token) -> `{order:Order, server_time:string}`. May finish a resource with a received code or email history, including while awaiting another message or while next-round status is uncertain. It does not refund successful usage. New allocation remains blocked until upstream completion is confirmed.
- POST `/api/orders/replace` body `{queue_minutes?:integer}` (Bearer token) -> `{token:string,order:Order,server_time:string}`. After the current resource terminates and `can_retry` is true, allocate another using the same CDK. The UI replaces its saved token with the returned token; no need to re-enter the CDK.
- Order: `{id,kind:"phone"|"email",status:"queued"|"allocating"|"waiting"|"received"|"next_pending"|"next_uncertain"|"complete_pending"|"completed"|"cancel_pending"|"cancelled"|"expired"|"review"|"failed",resource:string,code:string,codes:ReceivedCode[],mail_round:number,created_at,expires_at,cancel_after,can_retry:bool,can_next_code:bool,usage_limit:number,used_count:number,attempt:number,max_attempts:number,message:string,queue_expires_at?:string,queue_next_attempt_at?:string,queue_attempts?:number,queue_minutes?:number}`. `ReceivedCode` is `{round:number,code:string,received_at:string}`. `code` represents the current round; `codes` preserves all received rounds. User sees sanitized server messages.
- Email `no_stock` with a certain rejection automatically queues the same order, using its frozen purchase request. Retry interval is 5 seconds and the default queue deadline is 10 minutes from the initial request. Optional queue_minutes is an integer from 1 to 1440; missing/null uses the default. Existing queue deadlines remain unchanged on upgrade. `queue_attempts` counts allocation attempts including the first; it is not CDK usage. Queue fields describe local scheduling, never upstream rank or guaranteed capacity. A dedicated server worker continues when pages are closed and resumes queued orders after restart. GET/poll/duplicate POST do not create new purchases outside that worker. Successful allocation starts the original resource TTL then, capped by any earlier provider deadline; queue time does not reduce it. Cancellation/queue expiry consume no quota. Check CDK expiry/disabled/quota before retry. Non-stock definite failures stop; uncertain results and interrupted `allocating` become review without replay. Existing historical failures are not queued automatically.
- Phone certain `no_stock` retries keep the original country, channel and price. The ten-second stock window limits starting another purchase, never cancels one already sent. Each attempt has its own 25-second app context tied to shutdown; SMSBower retains its 20-second HTTP timeout. Only a final certain stock rejection after the window hides the channel for ten minutes. Unknown results retain the original order in review without replay. Allocation uncertainty audits contain only resource kind, allowlisted reason and elapsed milliseconds, never raw errors, URLs, credentials or response bodies.
- `usage_limit` is the maximum number of successful distinct resources for a CDK, from 1 to 1000. Each resource consumes 1 on its first valid upstream code only. Polling, subsequent messages for that same mailbox, and confirmed no-code cancellations do not consume more. No-code cancelled allocations can be replaced repeatedly without an attempt-count cap, subject to CDK expiry, availability, and normal request limits. The `attempt`/`max_attempts` fields remain for older clients and historical information; new UI never presents them as quota.
- Each email activation may receive up to 3 messages via the provider's next-message action, a local limit. After the first and second receipts, the backend worker automatically starts the next round; it continues without an open browser and resumes persisted receipts after restart. The third receipt stays available for manual completion or existing expiry handling. Remaining messages for an existing mailbox are allowed even if `used_count === usage_limit`. Each valid mailbox counts once, not once per email message. Upstream resource capabilities and expiry may prevent subsequent messages; continuation never extends the fixed expiry.
- Definite next-round rejections permit at most 3 automatic attempts per round, 30 seconds apart, persisted in `order_auto_mail`. Unknown results are never replayed. Automatic and manual actions share the owning order lock and durable `next_pending` transition; stale manual rounds return the current order. `Order` adds optional `auto_next_state:"pending"|"retrying"|"failed"` and `auto_next_at` (RFC3339, retrying only) while continuation is allowed. Both public and administrator UI show brief automatic preparation/retry text, hide the normal next-message button, and show “重试接收” only for `failed`, using the existing next-code endpoint. Keep receipt history, completion and uncertain-state verification available.
- `next_pending`, `next_uncertain`, and `complete_pending` are active states and continue normal polling. `next_uncertain` prohibits another next-code action but permits completion or administrator verification. `complete_pending` prevents replacement until completion is confirmed. Keep history visible and separately copyable in all these states.
- Completion intent and retry timing are persisted in `order_completions`. Pending email completion first uses the provider's read-only status endpoint; only confirmed completion settles the order, without adding receipts or charging quota again. Status lookup outages do not replay completion requests. Automatic confirmation is bounded to about two minutes from the original intent across restarts; explicit rejection or unresolved expiry moves to `review` and keeps replacement blocked. Legacy pending orders start this bounded window on their first upgraded refresh. Transport calls already in flight may finish after the deadline.
- Demo: `DEMO-PHONE` and `DEMO-EMAIL`, clearly labeled. Initial mock code appears after about 15 seconds. Demo phone can cancel after 10 seconds. The demo supports persisted receipt rounds and the same quota rules without paid requests.

## Admin API

- GET `/api/admin/bootstrap` -> `{setup_required:bool}`. Reads whether singleton administrator exists; does not claim ownership.
- POST `/api/admin/setup` `{password,confirm_password}` -> `{ok:true}` and authenticated cookie. First successful submission atomically creates the only administrator; later attempts return 409. Password is 12–128 Unicode characters, persisted as salted PBKDF2-SHA256 hash in SQLite. No password environment variable or newly generated credential file.
- POST `/api/admin/login` `{password}` -> `{ok:true}`; HttpOnly SameSite Strict cookie.
- GET `/api/admin/session` -> `{authenticated:true}` or 401.
- GET `/api/admin/balance` -> `{balance:string|null,currency:"USD",mode:"live"|"demo",updated_at:string|null,available:boolean,message:string,status:"available"|"unavailable"|"unconfigured"|"demo",server_time:string}`. Administrator authentication is required. Amounts are exact decimal strings from the provider, never inferred from allocation or cancellation actions. Missing configuration and query failures return null, not zero. Successful results cache for 15 seconds, failures for 5 seconds; concurrent requests coalesce and credential changes use separate cache entries. `?refresh=1` bypasses successful cache after a 2-second minimum refresh interval, retaining failed-result throttling. The administrator header refreshes while visible and after relevant resource actions; public pages never request or display account balance.
- POST `/api/admin/logout` -> `{ok:true}`.
- GET `/api/admin/resources` -> `{orders:Order[],server_time}`: the most recent administrator resource of each kind, at most two. POST the same path with `{kind:"phone"|"email",request_id:string,queue_minutes?:integer}` to allocate without a CDK or CDK quota. A durable request ID (16–128 alphanumeric, underscore or hyphen characters) returns the original result on retries, even after that resource ends. At most one unsettled direct resource of each kind is permitted; a concurrent different request ID resumes that resource and remembers the mapping. A new explicit request ID permits another resource after a confirmed terminal state.
- GET `/api/admin/resources/{id}` refreshes an administrator resource. POST `/{cancel|complete|next-code|queue-wait}` on that path uses existing lifecycle rules, with `{round}` for next-code and `{queue_minutes}` for queue-wait. These endpoints require administrator cookie authentication; public bearer sessions cannot access administrator resources, and these orders never return a public token. Order adds `source:"admin"|"cdk"` and optional `request_id`; administrator quota fields are zero and omitted from the UI.
- Administrator direct allocation uses configured service/country/domain/price/TTL and requires a configured upstream; public redemption enable/disable switches do not restrict it. It retains cancellation timing, receipt history, up to three email messages, restart recovery, uncertain-result review and credential-rotation protection. It does not issue any hidden CDKs or change CDK totals.
- Administrator allocation validation that rejects a new request before any order intent is persisted returns HTTP 409 with `code:"admin_allocation_rejected"`. Existing request IDs and active resources are resolved before this validation. Only this explicit rejection (or ordinary malformed-request 400/422) permits the frontend to discard the matching pending request; network/5xx/unknown results preserve its ID and original channel for safe recovery. Legacy pending phone requests missing channel metadata may use the selected channel while retaining the same request ID. Another tab's newer pending request must not be cleared by a delayed response.
- GET `/api/admin/overview` -> `{stats:{total,available,active,completed,review},orders:AdminOrder[]}` recent 50.
- GET `/api/admin/cdks?query=&status=&page=1` -> `{items:CDK[],total,page,page_size:50}`
- POST `/api/admin/cdks` `{kind:"phone"|"email",quantity:1..200,note:string,expires_days:1..365,usage_limit:1..1000}` -> `{codes:string[],batch_id:string,export_url:string}`. Codes remain viewable and copyable in the authenticated admin list. Complete codes are stored with authenticated encryption; hashes still validate redemption. Legacy `max_attempts` input is accepted as `usage_limit` when the latter is absent/zero, for upgrade compatibility. A random authenticated download URL remains valid in memory for 10 minutes (cleared on process restart). Type, country/domain/price/timeout snapshotted from settings at issuance.
- GET `/api/admin/exports/{token}` requires admin cookie; returns UTF-8 BOM CSV attachment, never puts plaintext CDKs in URL.
- POST `/api/admin/cdks/{id}/code` `{code:string}` -> `{ok:true}`. Backfill a legacy full code only after verifying its hash matches the existing CDK. Never derive or fabricate plaintext from a stored hash. A successful old-code redemption also backfills the encrypted full code automatically.
- POST `/api/admin/cdks/{id}/disable` -> `{ok:true}` (only available codes).
- GET `/api/admin/settings` -> Settings plus `{mode,api_configured:bool,api_base:string}`. Never returns the API key.
- PUT `/api/admin/settings` with Settings plus optional `{api_key:string}` -> Settings plus `{mode,api_configured:bool,api_base:string}`. Omitted or whitespace-only `api_key` preserves the saved key; a nonblank value is trimmed, validated as 8–512 printable non-space ASCII characters, encrypted and saved atomically with Settings, then applied immediately without a restart. `api_configured` reports a saved credential, not a successful upstream account check. The UI uses an empty password input and clears it after a successful save.
- API keys use AES-GCM encryption in SQLite metadata, with a dedicated encryption key derived from the existing `secret.key`. They never appear in returned settings, public config, or CDK snapshots. Startup imports legacy `SMSBOWER_API_KEY` only when no saved key exists; the database credential takes precedence thereafter. Back up the entire data directory, including `secret.key`.
- Replacing an existing API key is rejected with 409 while any order is `queued`, `allocating`, `waiting`, `received`, `cancel_pending`, `review`, `next_pending`, `next_uncertain`, or `complete_pending`. Saving the same key or leaving it blank is allowed. A missing initial credential can still be supplied while such orders exist, allowing their processing to resume. Rotation is serialized with provider operations so in-flight orders cannot switch accounts mid-request.
- POST `/api/admin/orders/{id}/resolve` `{resolution:"released"|"consumed"}` -> `{ok:true}`. Only `review` or `next_uncertain` status; manual upstream verification is required. `released` confirms a no-code resource was released; `consumed` ends the resource and counts it once. Previously counted resources are never charged again. A resource with its own `code` or `codes` history cannot be released for quota restoration; disable that radio choice in the UI. Do not use the CDK-wide `used_count` to make this decision, since earlier resources may have been successful. Admin UI shows a confirmation dialog with clear choice.
- Settings: `{brand:string,phone_enabled:bool,email_enabled:bool,phone_service:string,email_service:string,phone_country:string,email_domain:string,phone_max_price:string,email_max_price:string,phone_ttl_minutes:number,email_ttl_minutes:number,background_type:"none"|"image"|"video",background_url:string}`.
- GET `/api/admin/updates` returns update state, including current/latest version, repository, release URL, availability, installation support, phase, error, last check time, `downloaded_bytes`, `total_bytes` and `{auto_check,auto_update}` settings. Byte counters reset at the start of each accepted operation; download bytes reflect successful writes, and total bytes come from release asset metadata. PUT `/api/admin/updates/settings` accepts those two booleans; automatic installation implies automatic checking. POST `/api/admin/updates/check` performs a release metadata lookup. POST `/api/admin/updates/apply` returns 202 when installation starts; active orders or an unavailable/unsupported update return 409. All four require administrator cookie authentication; mutations retain same-origin protection. Client-supplied version/archive URLs are not trusted inputs.
- A live instance may start before its API key is configured. It reports `configured:false`, blocks new CDK issuance and purchases, and never substitutes a demo provider.
- CDK: `{id,batch_id,code?:string,masked_code,kind,status:"available"|"active"|"used"|"disabled"|"review"|"exhausted",note,created_at,expires_at,usage_limit,used_count,attempts,max_attempts}`. `code` is admin-only and is absent for legacy hash-only records until backfilled. Show the masked value and a brief backfill control for those records; never imply the missing code can be recovered from its hash.
- AdminOrder: Order plus `{masked_code,cdk_code?:string,provider_id:string,note:string}`. `cdk_code` is distinct from the order verification `code`.

## Storage and upgrade

Mailbox wait defaults to 25 minutes; phone wait remains 20 minutes. A transaction marked `email_wait_25_minutes_v1` upgrades existing email settings, email CDK snapshots and unallocated queue requests only when their old value was 20 minutes. Custom values and later administrator edits remain intact. Existing allocated deadlines are never extended because historical records do not identify upstream expiry caps; stock-queue deadlines also stay unchanged.

New full CDKs use AES-GCM encryption with a dedicated key derived from the existing data directory's `secret.key`. Hashes continue to support lookup and validation. Full codes appear only in authenticated admin responses, generation/export results, and the holder's submitted redemption request; do not place them in logs, public order responses, or download URLs. Back up SQLite and `secret.key` together.

Schema migration copies legacy `max_attempts` to `usage_limit`. Historical received-code or administrator-confirmed consumed orders are counted once each, and old single-code receipts are added as round 1 history. Migration and backfill run transactionally and only for newly introduced columns, so repeat startup never charges historical receipts again. Old attempt counts do not cap further no-code replacement. Legacy hashes are irreversible: original full codes must be provided by the holder or administrator to backfill encrypted display values.

Administrator resources use NULL `orders.cdk_id` and an `admin_resource_requests` mapping table. The migration transaction rebuilds the existing orders table to permit NULL, retaining existing order rows, receipt fields, row ordering, indexes and triggers. Existing CDK foreign keys remain enforced. A partial unique index enforces one unsettled administrator order per kind.

Email allocation intent is stored atomically with the new order in `order_allocation_queue`: original Request (no credential), deadline, next attempt, attempt count, and first queued time. Each retry persists `allocating` before contacting upstream. Email orders with a persisted allocation intent expose queue_minutes; only orders actually queued expose queue timestamp and attempt metadata, retained for their history. Migration adds the table without changing old orders; historical failures never become queued. Background allocation uses a separate pool of two workers, independent of OTP polling.

## Provider package

Package `internal/provider`. Export interface `Client` with `Allocate(context.Context, Request) (Activation,error)`, `Poll(context.Context,kind,id string) (Result,error)`, `Cancel(context.Context,kind,id string) error`, `Complete(context.Context,kind,id string) error`.
Optional `NextCodeClient` adds `NextCode(context.Context,kind,id string) error` for reusing an active mailbox. SMSBower uses email `setStatus` with `status=5`; the application enforces the three-receipt local limit and persists `next_pending` before calling upstream. Unknown outcomes transition to `next_uncertain` without replay. Optional `RoundPollClient` adds `PollRound(context.Context,kind,id string,round int) (Result,error)` so the stateless demo can recover persisted rounds after restart.
`Request {Kind,Service,Country,Domain,MaxPrice string; TTL time.Duration}`.
`Activation {ID,Resource string; ExpiresAt,CancelAfter time.Time}`.
`Result {Status,Code string}` receipt status `waiting`, `received`, `cancelled`, `expired`. Optional `CompletionStatusClient.CompletionStatus(context.Context,kind,id)` uses the read-only email status endpoint and returns `completed` only for confirmed completion; otherwise `waiting`, without returning a code. Local wait defaults are 25 minutes for email and 20 minutes for phone, capped by any explicit earlier provider expiry; they are not a promise of upstream lifetime.
`Error {Code,Message,DiagnosticReason string; Uncertain bool; RetryAfter time.Duration}` implements error. DiagnosticReason is an optional controlled transport label for private audit classification, never a raw cause. Uncertain allocation means NEVER auto retry/release CDK: upstream may have charged. Known no-stock/bad-key/etc allocation rejections safe. Cancellation errors never release CDK except verified already cancelled/expired. HTTP failures/timeouts/invalid allocation response conservative Uncertain=true. Ensure no URL/key leaks.
`NewSMSBower(baseURL,apiKey string) (*SMSBower,error)` uses trusted configured base, public default `https://smsbower.page`; `NewDemo() Client`. Demo provider IDs encode timestamps/kind in recoverable form so process restart does not lose active demo orders. Demo code 15 sec after allocate, cancel delay 10 sec.
Provider validates status responses; unexpected/malformed bodies are errors. NO arbitrary fallback service or price. Verify OpenAI phone and mail service codes independently using official documentation. Provider tests own package.

## Program updates

Releases come from `MengStar-L/OpenAIMailTransaction`. Stable tags trigger GitHub Actions builds; platform archives include the embedded frontend and are accompanied by SHA-256 checksums. Linux installer defaults to `/opt/shiguang`, uses systemd, enables automatic checking/installation on first install and preserves existing update preferences on upgrade. The manager checks every 6 hours and defers installation while orders are active. Before installing, it serializes with provider operations and blocks new redemption, replacement and administrator purchases; failed/deferred installation clears that maintenance gate.

Installation verifies the downloaded archive and extracted executable, preserves a `.previous` binary, and leaves configuration, credentials and data in place. Linux systemd restarts the service; Windows uses a detached helper. The helper may restore the previous binary after an immediate launch failure; this is not HTTP health-based rollback. A plain `dev` source build and the current Docker build support checking only; update containers by rebuilding/replacing the image. Update settings are stored in `DATA_DIR/update-settings.json`. See [installation instructions](docs/INSTALL.md) for service permissions and backups.
